When the Same Android Device Behaves Differently: Debugging a Production Flutter ERP App

Project: ERP for BYD — used daily by 100+ employees across Nepal

One of the most interesting problems I encountered while maintaining a production Flutter ERP application wasn't related to business logic, UI rendering, or even the backend.

It was a device-specific startup issue.

The strange part? Multiple users were running the application on the same phone model with seemingly identical hardware specifications, but only certain users experienced a blank screen during startup.

This turned into an investigation involving GPU rendering, Android device configuration, application data, plugin initialization, and eventually SharedPreferences.

1. The Problem: Same Device, Different Behaviour

The issue was initially reported by a client who experienced a blank screen when opening the application. Since this was a production ERP application, the issue was particularly important — users depended on it for their daily business operations.

I started by collecting device information and asking some basic diagnostic questions:

  • What exactly happens when you open the application?
  • Does the application remain on a blank screen?
  • Have you tried reinstalling it?
  • Are other users experiencing the same behaviour?

What made things confusing was the device comparison. Some users with the same phone model and hardware specifications were using the application without any problems. However, User D and another user were experiencing startup issues. This made me realize that comparing hardware specifications alone wasn't enough.

2. First Hypothesis: Impeller and Mali GPU Drivers

I started researching potential compatibility issues based on the affected devices' specifications. During that investigation, I came across reports of Impeller-related issues involving Mali GPU drivers.

Interestingly, I had recently upgraded Flutter to maintain version consistency across the project and discovered that Impeller was being enabled. I decided to force Skia instead of Impeller to investigate whether the rendering engine was responsible.

The result was interesting. The application started working on one affected user's device, but User D continued experiencing the same problem.

This was a partial resolution, not the root cause. It also taught me an important debugging lesson: a successful fix for one reproduction case doesn't necessarily explain every occurrence of the same symptom.

3. Expanding the Investigation

Instead of randomly changing configurations, I started documenting possible causes. My investigation checklist included:

  • Android runtime permissions
  • Plugin initialization phases
  • BLoC initialization inside main()
  • Splash screen rendering and triggering
  • Operations blocking application startup
  • Device-specific plugin compatibility

I wanted to understand whether the application was actually failing to render or simply never reaching the stage where the UI could be displayed. That distinction became important later.

4. Another Client, Another Clue

During the investigation, another client contacted me after updating their device. They reported a similar application startup issue. I suggested reinstalling the application, but that didn't solve it. I then suggested clearing the application's cache and data — this time, the application started working again.

This introduced another possibility: persisted application data could also contribute to startup problems.

I subsequently disabled Android application backup using android:allowBackup="false" as a preventive measure against restoring potentially problematic application data. However, User D's issue remained unresolved.

5. Investigating Plugin Initialization

I cloned the project to isolate the issue and started looking closely at how plugins were initialized. The existing approach was straightforward:

await initializePluginA();
await initializePluginB();
await initializePluginC();
await initializePluginD();

This approach works perfectly well when initialization tasks are quick and their execution order is necessary. However, there was a potential architectural problem: every operation depended on the previous operation completing.

If one plugin took unusually long to initialize, every subsequent operation had to wait. With multiple plugins involved in application startup, this could become a significant bottleneck — leaving the user staring at a blank screen.

6. Rethinking the Initialization Lifecycle

I decided to change how initialization was handled. Rather than making every plugin depend on the completion of another plugin, I isolated independent initialization tasks. The new approach focused on:

  • Independent asynchronous initialization
  • Individual timeouts for plugins
  • Better failure handling
  • Preventing one plugin failure from blocking unrelated initialization
  • Improving plugin lifecycle compatibility

The objective was to make the application more resilient. A plugin that failed or took too long shouldn't automatically prevent unrelated parts of the application from progressing. Of course, not every initialization operation can run independently — some plugins have genuine dependencies, and those must still be respected. The goal wasn't simply to initialize everything simultaneously. It was to remove unnecessary dependencies.

7. Finding the Actual Bottleneck

After isolating the initialization process and investigating individual plugins, I eventually identified the problem.

SharedPreferences initialization was taking unusually long on User D's device.

It wasn't necessarily throwing an exception or crashing the application. It was taking too long to initialize. Because the startup sequence was waiting for this operation, the application couldn't progress to the next stage. Consequently, the splash screen was never triggered, leaving the user with a blank screen.

This was an important discovery. The issue wasn't in the rendering engine or the UI itself — the application was getting blocked much earlier in its startup lifecycle.

I investigated the plugin's lifecycle, made the necessary compatibility changes, and released an updated version. Finally, User D confirmed that the application was working.

8. What I Learned

Hardware specifications don't tell the whole story.

Two identical devices can have different runtime behaviour because of their OS configuration, permissions, persisted data, and environment.

Sequential initialization isn't always the right approach.

When multiple independent plugins are required, unnecessary sequential dependencies can increase startup latency.

Plugin failures should be isolated.

One plugin should not unnecessarily prevent unrelated application functionality from starting.

Timeouts are important.

An initialization task should not be allowed to block application progress indefinitely.

A blank screen doesn't always mean a rendering problem.

Sometimes the application never reaches the stage where rendering can even begin.

Conclusion

What initially appeared to be a device-specific rendering issue eventually led me to investigate the application's startup architecture. The investigation involved multiple hypotheses, partial fixes, additional client reports, and eventually isolating the actual initialization bottleneck.

The biggest takeaway for me was simple: application startup is an engineering problem of its own.

It isn't enough for plugins to work individually. Their initialization order, dependencies, failure handling, and interaction with the application lifecycle matter just as much. A production application should be designed to handle slow or failing dependencies without unnecessarily taking the entire user experience down with them.

And sometimes, the most difficult bugs aren't caused by what your application does — but by what it is waiting for.
